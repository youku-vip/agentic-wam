# 用户上传同步客户端：审查与修正

基于上传的完整environment.rtc_client_agenticwam代码制作，未运行真实机器人或在线模型。附件原文保持不变。修正版在本目录rtc_client_agenticwam.py；用于替换客户端Python包内同名模块，不是服务端custom34_server.py。

## 启动参数的实际含义

- async_mode=false、use_rtc=false：走同步run_loop_sync，不启动后台推理任务，不发送RTC前缀。
- H=32：检查服务端返回[32,20]。
- s_min=20：每次只执行前20步，后12步弃用；此前仅看服务端无法判定实际执行步数，现已由客户端确认。
- max_hz=10：20步的名义动作执行时间约2秒，实际还受env.step耗时、推理等待、恢复动作等影响，并非连续端到端10Hz。
- beta=10.0：当前源码中仅保存为属性，正常同步动作没有使用它做平滑，不能通过调beta改善这个同步路径。
- loguru默认只输出WARNING及以上，info中的整块action打印通常被过滤，不能把它当作已确认的运行时I/O瓶颈。

## 已确认的问题与改动

1. 原同步循环顶部推理，执行20步后底部再推理，下一轮顶部又推理覆盖底部结果。正常情况下请求数约是实际使用动作块数的两倍。修正为每块开头采集新观测并推理一次，底部不再生成无用动作。
2. 前19步get_obs=False，但原夹爪异常判断反复读取上一块obs.arm_actpos。修正为只在有新返回obs时判断；当前采样策略仍是块末一次。没有新增逐步图像读取，也不声称现在有每步实时夹爪反馈。
3. 原initial_pose_obs在整个进程只保存一次。修正为按episode刷新并deepcopy，任务切换/明确空闲恢复/回放结束/环境重置后不再回到上个任务的初始姿态。
4. 原server reset只在connect及instruction字符串变化时调用。同指令清空后重启、回放、环境done/truncated等未同步清理远端。新增串行reset_episode，并在明确新episode开始前调用，避免每个act都reset。
5. 夹爪稳定器在新episode和异常恢复后重置，不让旧15步锁跨episode延续。
6. 已执行的正常动作立即计入step，done/异常中断也计数，防止总步数失真。done/truncated优先于额外异常恢复动作处理。
7. 控制周期计时包含本步动作转换等处理，而不仅是env.step；仍为同步模式，没有把推理等待隐藏成连续10Hz。

## 没有更改、仍需核实

- 默认夹爪阈值0.5、稳定锁15步保持原值。锁是按控制步递减，不按墙钟时间；模型闭合/释放可能被延迟，需结合原始预测与实际命令日志评估。
- 保留原来的arm_actpos<50触发打开/恢复逻辑及原恢复动作，只修正反馈新鲜度与参考姿态生命周期。<50不一定证明抓取失败，取决于夹爪和物体；两臂同时打开/恢复也需用户自行确认适用性。
- 未修改trans_utils的Euler/rot6D实现、相机颜色约定、控制器行为、checkpoint或统计。训练的rot6D为旋转矩阵前两列，客户端转换实现是否一致仍需核对。
- 新鲜env.get_obs不保证相机与状态同步，底层传感器时间戳未提供。
- 同一非空指令持续运行不会自动判断一轮任务完成；需上层明确清空指令、任务切换、环境done或重置。仅推送同一字符串不等于新episode。
- 上传的是客户端启动命令，不是服务器命令。服务端是否fast-joint、joint目标、历史开关及模型版本仍需查看实际启动配置。
- 这些确定的客户端缺陷不证明“只重启服务端就恢复”的唯一原因。若客户端不重启而服务器重启能稳定恢复，还需排查服务器状态、随机采样、延迟和重复请求路由。

## 在客户端机器安装

先停止客户端控制循环。确定实际模块文件位置：

```bash
PY=/usr/local/bin/python3.11
"$PY" - <<'PYCODE'
import importlib.util
print(importlib.util.find_spec('environment.rtc_client_agenticwam').origin)
PYCODE
```

备份打印出的文件，将修正版覆盖到该位置；不是覆盖服务器文件。请保留本地其他改动，必要时对比diff后合并。启动命令可继续使用现有同步参数，不需要开启RTC。暂不同时修改s_min、夹爪锁和模型配置，先比较同条件试验。

如果需要测试更短闭环间隔，可在受控验证中单独将s_min从20改为10或更小，H保持32不变；代价是请求更频繁、更多推理停顿，不保证一定提高成功率。

## 验证

```bash
python -m pytest deploy-custom/test_sync_client_control.py -q
python deploy-custom/test_custom34_rtc_adapter.py
```

同步测试通过AST提取实际run_loop_sync和稳定器，只注入模拟env、client，不导入机械臂SDK、不控制真实设备；覆盖一块一次推理、旧夹爪反馈不误触发恢复、done计数和远端reset、新任务恢复姿态。原有HTTP/RTC测试使用本地假服务，验证协议及异步前缀对齐；没有验证真实动作、SDK、相机或抓取成功率。

实机观察：每执行20步正常动作应对应一条有效/act请求，不再中间多出一条被丢弃的预测。新episode会有reset日志，连续同一episode的每块不会reset。比较推理延迟、真实命令间隔、夹爪预测与最终稳定命令，以及同样初始场景下的多轮成功率。
